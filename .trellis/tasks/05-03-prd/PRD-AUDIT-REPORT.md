### 1.2 Next.js 16 App Router

#### ✅ 符合约定的部分

- Route groups: `(auth)`, `(student)`, `(teacher)`, `(admin)` ✅
- 文件约定: `layout.tsx`, `page.tsx`, `route.ts` ✅

#### ❌ 问题与冲突

| 问题 | 严重性 | 描述 | 建议 |

**结论**: Next.js 16 的使用基本正确，但存在架构冲突和缺失的标准文件。

## 二、架构审计结果

### 2.1 深度模块评估

PRD 第 10 章定义了 7 个深度模块，评估如下：

| 模块 | 必要性 | 复杂度 | 建议 |
|------|--------|--------|------|
| **M1: AI Pipeline** | ⚠️ 中 | 高 | **简化**：直接在 API Route 中调用 AI SDK，无需封装 |
| **M2: Bloom Engine** | ✅ 高 | 中 | **保留**：纯数据转换，值得封装 |
| **M3: Challenge Engine** | ✅ 高 | 中 | **保留**：核心功能，需要封装 |
| **M4: Audit Pipeline** | ⚠️ 中 | 中 | **简化**：可以合并到数据层 |
| **M5: Provider Registry** | ❌ 低 | 高 | **删除**：过度抽象，直接使用 AI SDK 的 Provider |
| **M6: Org Manager** | ⚠️ 中 | 中 | **简化**：可以合并到数据层 |
| **M7: Dataset Export** | ✅ 高 | 低 | **保留**：独立功能，值得封装 |

**结论**: 7 个深度模块中，只有 3 个（M2, M3, M7）真正必要，其余 4 个是过度设计。

### 2.2 目录结构评估

#### PRD 要求（第 5.2 节）

```
src/
├── app/              # 仅路由
├── features/         # 按功能域组织
│   ├── chat/
│   ├── cognitive-path/
│   ├── challenge/
│   ├── audit/
│   └── dashboard/
├── components/
│   ├── ui/
│   └── shared/
└── lib/
    ├── ai/
    ├── supabase/
    └── db/queries/
```

#### 实际实现

```
src/
├── app/              # 路由 + 部分逻辑
├── components/
│   ├── ui/
│   └── workbench/    # 业务组件
├── hooks/
└── lib/
    ├── data/         # 数据层
    ├── supabase/
    └── observability/
```

#### 评估

| 方面 | PRD 设计 | 实际实现 | 评价 |
|------|---------|---------|------|
| **复杂度** | 高（5 层嵌套） | 低（3 层嵌套） | ✅ 实际更简洁 |
| **可维护性** | 中（功能域隔离） | 高（扁平结构） | ✅ 实际更易维护 |
| **必要性** | 低（过度抽象） | 高（实用主义） | ✅ 实际更合理 |

**结论**: 实际的扁平结构比 PRD 的 `features/` 结构更合理，无需重构。
